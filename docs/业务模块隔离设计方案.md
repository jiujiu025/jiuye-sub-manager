# 业务模块隔离设计方案

## 1. 设计目标

本方案用于在保留现有 `/sub/{token}`、旧套餐和旧 Token 的前提下，逐步增加客户、经理、销售和通知能力。

核心原则：

- 每个业务模块拥有自己的数据和服务边界。
- 模块之间只通过明确的服务接口和只读查询协作。
- 新功能采用增量迁移，不直接改写旧套餐核心逻辑。
- 订阅 Token 的签发、轮换和撤销只能由订阅模块负责。
- 前端页面按业务模块拆分，避免所有功能继续堆在套餐页面。

## 2. 模块边界

### 2.1 身份与权限模块

负责用户登录、密码、角色和访问控制。

角色：

- `admin`：系统管理和业务分配。
- `manager`：只管理分配给自己的客户和订阅。
- `user`：只查看自己的订阅。

本模块不负责套餐节点筛选，也不负责生成订阅内容。

### 2.2 来源模块

负责上游来源 URL、同步状态、同步日志和来源级配置。

本模块可以写入节点池，但不能修改套餐、客户或 Token。

同步失败时保留上一次成功节点，不主动清空节点池。

### 2.3 节点池模块

负责自有节点和上游节点的标准化存储、启停、编号、备注和去重。

节点来源使用现有字段区分：

- `custom`：自有节点。
- `upstream`：上游来源节点。

计划新增字段：

- `node_code`：业务编号，删除后不复用。
- `note`：管理备注。
- `last_seen_at`：上游最后发现时间。

节点模块不负责客户归属，不直接修改订阅 Token。

### 2.4 套餐方案模块

套餐方案是可重复销售的配置模板，负责：

- 套餐名称和编号。
- 地区和节点筛选规则。
- 有效期规则。
- 价格模板和管理备注。
- 套餐复制。

套餐方案不保存具体客户、销售记录或客户独立 Token。

现有 `packages` 暂作为兼容层，不立即重命名或删除。

### 2.5 客户模块

负责客户档案，不负责订阅节点内容。

客户资料包括：

- 客户编号和名称。
- 联系方式。
- 地区、标签和备注。
- 首次购买时间和最近购买时间。
- 默认经理。
- 客户状态。

客户档案可以先创建，之后再绑定登录账号。

### 2.6 客户订阅模块

负责一次实际开通记录，负责：

- 客户和套餐方案关联。
- 开通时间和到期时间。
- 销售价格和成本价格。
- 订阅状态。
- 独立 Token 的签发、轮换和撤销。
- `/sub/{token}` 的兼容访问。

一个套餐方案可以产生多个客户订阅；一个客户可以拥有多个订阅。

### 2.7 经理分配模块

负责客户和订阅的负责人关系：

- 客户默认经理。
- 订阅指定经理。
- 经理转移。
- 待分配订阅。

归属优先级：

```text
订阅指定经理 > 客户默认经理
```

本模块不修改节点和来源数据。

### 2.8 通知模块

负责站内收件箱和定时提醒，不参与业务状态判断。

通知由其他模块产生业务事件，再由通知模块落库和去重：

- 到期前三天。
- 当天到期。
- 已停机。
- 新客户或新订阅分配。
- 经理变更。
- Token 撤销。
- 来源同步失败。

通知使用业务唯一键，避免重复发送。

## 3. 数据关系

```text
User
 ├── ManagerProfile
 └── CustomerAccount（可选）

Node / Source
      ↓
Plan（套餐方案）
      ↓
Subscription（客户订阅）
      ├── Customer
      ├── Manager
      └── SubscriptionToken
```

节点与套餐是多对多关系。第一阶段可以兼容现有 `package_rules.node_ids`，后续使用独立关联表支持可靠的使用关系查询。

## 4. 管理员开通流程

```text
选择套餐方案
  ↓
选择客户、经理或暂不分配
  ↓
设置开通时间、到期时间和价格
  ↓
创建客户订阅
  ↓
生成独立 Token
  ↓
记录审计日志并创建通知
```

管理员可以直接开通并分配给客户，也可以先分配给经理，等待经理绑定客户。

## 5. 套餐复制规则

复制套餐方案时复制：

- 节点和来源筛选规则。
- 地区、有效期和价格模板。
- 管理备注。

不复制：

- 客户和经理归属。
- Token 和访问记录。
- 销售记录。
- 到期状态。

副本生成新的套餐编号，默认状态为待分配。

## 6. API 分层

接口按业务归属拆分：

```text
/api/auth/*
/api/sources/*
/api/nodes/*
/api/plans/*
/api/customers/*
/api/subscriptions/*
/api/managers/*
/api/notifications/*
/sub/{token}
```

`/sub/{token}` 保持现有兼容入口。订阅响应只调用订阅服务，不直接拼接客户、经理和套餐页面逻辑。

## 7. 服务调用规则

模块之间只允许以下类型的依赖：

- 认证模块提供当前用户和权限判断。
- 节点模块提供节点只读查询。
- 套餐模块提供筛选规则只读查询。
- 订阅模块调用节点和套餐的只读服务生成内容。
- 通知模块接收事件并保存通知。

禁止：

- 前端直接拼装 Token。
- 套餐服务直接修改客户表。
- 节点服务直接撤销 Token。
- 通知任务直接改变订阅状态。
- 经理页面绕过服务层查询其他经理数据。

## 8. 分阶段实施

### 阶段 0：契约和回归基线

- 固定旧 API 行为。
- 增加模块级服务接口。
- 建立旧 `packages` 到新订阅模型的兼容适配层。
- 记录现有测试基线。

本阶段不改变数据库结构。

### 阶段 1：套餐方案和复制

- 增加套餐复制接口。
- 复制规则但不复制 Token 和归属。
- 新增复制、隔离和权限测试。

这是最小风险的第一批功能。

### 阶段 2：客户与客户订阅

- 增加客户档案。
- 增加实际订阅记录。
- 每个客户订阅拥有独立 Token。
- 保留旧套餐和旧订阅链接兼容。

该阶段需要新增 migration，但只增加表和可空字段，不删除旧数据。

### 阶段 3：经理和管理员分配

- 增加 `manager` 角色。
- 管理员支持直接分配客户或经理。
- 增加经理数据隔离测试。
- 增加经理转移和待分配状态。

### 阶段 4：节点使用关系

- 自有/上游节点分栏。
- 节点编号、备注和更新时间。
- 节点被哪些套餐和客户订阅使用。
- 删除或禁用节点前显示影响范围。

### 阶段 5：通知中心

- 站内收件箱。
- 到期前三天提醒。
- 到期、停机、同步失败等通知。
- 通知去重和已读状态。

## 9. 每阶段必须验证

- 旧 `/sub/{token}` 不受影响。
- 管理员、经理、普通用户权限隔离。
- 一个节点可以被多个套餐使用。
- 一个套餐方案可以被多个客户购买。
- 每个客户订阅 Token 独立。
- Token rotation/revoke 不串联其他订阅。
- 到期后只影响当前订阅。
- 来源同步失败不会清空旧节点。
- 迁移可在新数据库和现有数据库执行。

## 10. 本轮决策

本轮只完成模块边界和实施设计，不修改现有业务代码、不新增 migration、不改变生产配置。

下一步优先实现“套餐复制”，因为它边界清晰、风险最低，可以先验证模块化服务和回归测试方式，再进入客户订阅模型。

## 11. 第二阶段详细设计：客户订阅

第二阶段不把客户字段继续堆到 `packages` 表，而是新增实际订阅概念。套餐方案负责“卖什么”，客户订阅负责“卖给谁、谁负责、卖了多久”。

### 11.1 计划中的数据表

#### `plans`

保存可重复销售的套餐方案：

- `id`、`code`、`name`、`description`。
- 节点和来源筛选规则。
- 默认有效期和价格模板。
- `status`：`draft`、`available`、`stopped`、`archived`。
- 创建人和更新时间。

#### `customers`

保存客户档案：

- `id`、`customer_code`、`name`。
- `contact_type`、`contact_value`。
- `region`、`tags`、`note`。
- `default_manager_id`。
- `status`：`active`、`paused`、`archived`。
- `first_purchase_at`、`last_purchase_at`。

联系方式必须单独保存，不能把手机号、邮箱或即时通讯账号拼到备注字段中。

#### `subscriptions`

保存一次实际开通：

- `id`、`subscription_code`、`plan_id`、`customer_id`。
- `manager_id`、`opened_by`。
- `started_at`、`expires_at`。
- `sale_price`、`cost_price`。
- `status`：`pending`、`active`、`suspended`、`expired`、`revoked`、`cancelled`。
- `note`、`created_at`、`updated_at`。

#### `subscription_tokens`

保存订阅 Token 生命周期：

- `subscription_id`。
- `token_hash`、`token_prefix`、`token_encrypted`。
- `created_at`、`last_access_at`、`last_access_ip`、`access_count`。
- `revoked_at`、`replaced_by_id`。

Token 必须独立于套餐方案，rotation 只影响当前客户订阅。

### 11.2 旧数据兼容

不立即删除或重命名现有 `packages`：

- 旧套餐继续由现有服务处理。
- 新订阅模型增加 `legacy_package_id` 可选关联。
- `/sub/{token}` 先按新 Token 查找，再兼容旧套餐 Token。
- 不对旧 Token 做批量轮换。
- 不自动猜测旧套餐的客户、经理和销售价格。

只有管理员明确执行“纳入客户订阅管理”时，才建立旧套餐与新订阅的关联。

### 11.3 管理员直开流程

```text
选择套餐方案
  ↓
填写客户或选择“待分配”
  ↓
选择经理（可选）
  ↓
填写开通时间、到期时间、销售价和备注
  ↓
创建 subscriptions
  ↓
创建 subscription_tokens
  ↓
写入审计日志
  ↓
向客户/经理创建站内通知
```

管理员可以：

- 直接分配给客户。
- 直接分配给经理。
- 创建待分配订阅。
- 修改客户和经理归属。
- 转移订阅负责人。
- 单独 rotation 或 revoke 当前订阅 Token。

### 11.4 经理绑定流程

经理只能处理分配给自己的待分配订阅：

```text
经理查看待分配订阅
  ↓
选择已有客户或新建客户档案
  ↓
绑定客户
  ↓
订阅变为 active
  ↓
客户和经理均收到站内通知
```

经理不能修改套餐节点规则、成本价、系统设置或其他经理的数据。

## 12. 状态和权限规则

### 12.1 套餐方案状态

```text
draft → available → stopped → archived
```

- `draft`：可以编辑，不能新开通。
- `available`：可以创建客户订阅。
- `stopped`：不能新开通，不影响已经有效的订阅。
- `archived`：只读保留历史记录。

### 12.2 客户订阅状态

```text
pending → active → expired
                  ├→ suspended
                  ├→ revoked
                  └→ cancelled
```

状态变更必须由订阅服务统一执行，页面不能直接修改数据库字段。

- 到期只影响当前订阅。
- Token revoke 不删除客户或销售记录。
- 重新生成 Token 不改变订阅的客户、经理和到期时间。
- 套餐方案停用不自动停用已经开通的客户订阅。

### 12.3 权限矩阵

| 操作 | 管理员 | 经理 | 普通用户 |
| --- | --- | --- | --- |
| 创建套餐方案 | 是 | 否 | 否 |
| 复制套餐方案 | 是 | 否 | 否 |
| 创建客户订阅 | 是 | 仅可处理自己权限范围内的待分配项 | 否 |
| 查看成本价 | 是 | 否 | 否 |
| 查看自己负责的客户 | 是 | 是 | 否 |
| 查看其他经理客户 | 是 | 否 | 否 |
| rotation/revoke Token | 是 | 仅限自己负责的订阅，需记录审计 | 否 |
| 管理来源和节点 | 是 | 否 | 否 |
| 查看自己的订阅 | 是 | 是 | 是 |

所有后端接口都必须重新执行归属判断，不能只依赖前端隐藏按钮。

## 13. 节点使用关系设计

### 13.1 直接选择

套餐规则中的 `node_ids` 表示直接选择的节点。一个节点可以被多个套餐使用。

### 13.2 来源筛选

套餐通过 `source_filter`、地区、类型和关键词间接使用节点。查询“节点被哪些套餐使用”时必须同时返回：

- 直接选择关系。
- 来源或规则筛选关系。

结果标记为：

- `direct`：直接选择。
- `rule`：通过筛选规则命中。

### 13.3 删除和禁用保护

删除或禁用节点前，后端返回影响摘要：

- 受影响套餐数量。
- 受影响客户订阅数量。
- 受影响地区。

默认只允许禁用，不建议物理删除正在被有效订阅使用的节点。确认删除时必须写入审计日志并精确失效相关缓存。

## 14. 通知中心详细设计

通知表建议包含：

- `recipient_user_id`。
- `type`、`title`、`content`。
- `related_type`、`related_id`。
- `dedupe_key`、`read_at`、`created_at`。

唯一去重键示例：

```text
subscription:{id}:expire-warning:{yyyy-mm-dd}
subscription:{id}:expired:{yyyy-mm-dd}
source:{id}:sync-failed:{yyyy-mm-dd}
```

定时任务只负责扫描和发布事件，不能在任务代码里直接拼接页面文案或修改多个业务表。

## 15. 页面信息架构

管理员端：

```text
概览
来源管理
节点管理
套餐方案
客户管理
客户订阅
经理管理
通知中心
系统设置
操作日志
```

经理端：

```text
我的概览
我的客户
我的待分配订阅
我的客户订阅
通知中心
个人设置
```

客户端：

```text
我的订阅
订阅二维码
到期时间
Token 状态
通知中心
个人设置
```

套餐方案页面只管理方案，不显示客户销售明细；客户订阅页面才显示客户、经理、销售价和到期状态，避免页面职责混杂。

## 16. 后续实现顺序

1. 先实现套餐复制并保持当前版本稳定。
2. 新增 `plans`、`customers`、`subscriptions`、`subscription_tokens` 的模型和 migration。
3. 完成管理员直开订阅，不先做客户登录。
4. 增加经理角色和经理数据隔离。
5. 增加节点使用关系查询和删除影响保护。
6. 增加站内通知及到期前三天提醒。
7. 最后增加客户登录和客户端展示页面。

每一步都必须满足：

- 旧 API 和 `/sub/{token}` 回归通过。
- 新 migration 可在新数据库和现有数据库执行。
- 失败事务不会产生半条订阅或明文 Token。
- 经理不能通过 ID、查询参数或导出接口越权。
- rotation、revoke、到期只影响目标订阅。

## 17. 当前不做的功能

- 在线支付和支付回调。
- 自动续费。
- 多级代理分佣。
- Redis、PostgreSQL、Celery 或消息队列。
- 短信、邮件和外部通知服务。
- 复杂节点主动探测。

这些功能会显著扩大数据和部署边界，暂不纳入本阶段。

## 18. 页面按钮审计基线

当前已有页面的按钮和接口应遵循以下检查规则：

- 刷新、查询和分页操作必须显示加载状态，不能重复提交。
- 删除、批量删除和复制等确认框取消时不得产生未处理异常。
- 列表刷新后清空旧选择，不能把已经离开当前列表的数据 ID 继续提交。
- 前端只负责隐藏入口，后端仍必须执行角色和对象归属校验。
- 只有 `admin` 角色进入管理员首页和管理员导航；未知角色默认进入用户入口。
- Token、节点凭证和来源 URL 只能通过受保护的按需接口获取。
- 空列表、接口失败和权限失效都必须有明确页面状态，不能只留下空白区域。

本轮审计已修复：

- 用户管理页面已加入管理员导航。
- 管理员角色判断改为严格匹配 `admin`。
- 登录页和路由守卫的角色跳转规则统一。
- 来源、套餐和节点删除取消不再产生未捕获 Promise rejection。
- 节点列表刷新后清空过期选择。

## 19. 下一阶段开发闸门

在实现客户订阅 migration 前，必须先完成以下只读确认：

1. 旧套餐列表、详情、预览、Token rotation/revoke 全部回归通过。
2. `/sub/{token}` 的 Clash、Mihomo、Sing-box、URI、Base64 输出全部不变。
3. 新增表只允许追加，不允许删除或重命名现有表和字段。
4. 新订阅 Token 查询失败时不能回退到其他客户或其他套餐。
5. 管理员直开事务失败时，客户、订阅和 Token 不能只创建其中一部分。
6. 经理和普通用户通过 ID、分页、导出、订阅地址接口都不能越权。

未满足以上闸门时，不进入生产数据库迁移，也不把新客户订阅页面接入正式导航。
